What actually happens when twitter-cli asks for your Keychain password

TL;DR. One dialog you clicked through traverses seven distinct layers — a UI prompt, a userspace daemon, an XPC boundary, a kernel-level keychain ACL check, an AES key release, a SQLite cookie blob, and finally an HTTPS replay against X. The operator-relevant question is "who in that stack is trustworthy and who is merely audit-able?" This doc peels the stack one boundary at a time and marks each layer with what you can verify yourself vs. what you must accept on mechanism.

ACL
Access Control List. Per-keychain-item list of code-signing identities permitted to read it without prompting.
AES-CBC
Symmetric block cipher in cipher-block-chaining mode. Chromium uses AES-128-CBC with a fixed 16-space IV.
Bearer token
An auth credential where mere possession proves identity. Twitter's auth_token cookie is one.
cdhash
Code-directory hash. The portion of a Mach-O signature that uniquely identifies a binary version. ACL entries compare against this.
Cookies sqlite
Chromium's per-profile cookie database. Names are plaintext; values are AES-encrypted blobs prefixed with v10.
ct0
Twitter's CSRF cookie. Must match the x-csrf-token header sent with API requests.
GraphQL (internal)
x.com's private API at /i/api/graphql/<query-id>/<op>. Not documented; query IDs rotate.
Keychain
macOS encrypted credential store. The "login" keychain is unlocked at user-login by your password.
PBKDF2
Password-Based Key Derivation Function 2. Stretches a password into a key. Chromium parameters: HMAC-SHA1, 1003 iterations, salt "saltysalt".
PKCS7 padding
Block-cipher padding scheme. The last byte indicates how many padding bytes to strip after decryption.
SecAccess
The Security.framework object representing an item's ACL. Inspect via Keychain Access.app.
SecKeychain
The C API in Security.framework (e.g. SecKeychainFindGenericPassword) that user processes call to request items.
securityd
The macOS daemon that owns keychain decryption, ACL enforcement, and prompt delegation. Runs as root.
Snowflake
Twitter's 64-bit unique ID format for tweets. Not part of the keychain stack — appears in URLs you fetch.
XPC
Apple's structured IPC over Mach messages. The protocol Python uses to reach securityd.
v10 prefix
Three-byte marker on encrypted cookie values indicating Chromium's current encryption scheme version. Strip before decrypting.

L1The dialog you clicked: who is actually asking?

The modal is a userland UI process, not the kernel — but it is the only layer where you have agency.

Responsible: SecurityAgent.app (Apple-signed, launched by launchd on demand). The text "security wants to use your confidential information stored in Microsoft Edge Safe Storage" is composed from the requesting binary's name and the keychain item's kSecAttrService.
Crosses in
A request handle from securityd naming the keychain item and caller PID.
Crosses out
Your typed password (UTF-8 bytes), or a Deny verdict. The bytes never return to the calling process.
Verify Run ps aux | grep -i securityagent while the dialog is up — you will see the helper alive only during the prompt.
Wrong mental model "twitter-cli is asking for my password." No. twitter-cli never sees, requests, or has any path to your login password. It asked securityd for a keychain item; securityd in turn asked SecurityAgent to confirm with you. You are authenticating to macOS, not to the Python process.

L2The calling process: what does Python actually invoke?

A user-space binary makes one library call and waits for bytes.

Responsible: the Python interpreter spawned by uv run twitter-cli, calling into Security.framework via ctypes (or, in the subprocess fallback, shelling out to /usr/bin/security).
# the literal subprocess fallback path
$ security find-generic-password -s "Microsoft Edge Safe Storage" -w
# macOS shows the Keychain prompt; on success, prints the AES-master-string
Crosses in (down)
A service name string ("Microsoft Edge Safe Storage") and the caller's own code-signing identity, auto-attached by libSystem.
Crosses out (up)
A base64-ish password string — the input to PBKDF2 at L7. Not the AES key itself.
Trust You can audit the open-source twitter-cli source for exactly this call and confirm it does nothing else with the returned string until L7 derivation.

L3The XPC hop: why does this need a daemon at all?

User processes cannot touch the keychain file directly. They must go through a privilege-separated broker.

Responsible: securityd (on modern macOS, technically trustd + secinitd + SecurityAgent; the umbrella behavior is unchanged for our purposes). Communication is Mach IPC framed as XPC messages.
Crosses in
An XPC dictionary: {op: find_generic, service: "Microsoft Edge Safe Storage", account: ..., audit_token: ...}.
Crosses out
Either the password payload or an errSecAuthFailed / errSecUserCanceled status code.
Verify log stream --predicate 'subsystem == "com.apple.securityd"' shows the request transit in real time.
Wrong mental model "The browser holds the AES key in memory, why doesn't it just hand it to other tools directly?" Because every requester is reauthenticated against the keychain item's ACL by an out-of-process daemon. The browser cannot delegate; securityd is the only authority. This is why a fresh Python interpreter triggers a prompt even though Edge is running and "knows" the key.

L4The ACL check: why your second run didn't prompt

Each keychain item has an access-control list of code-signing identities. New identities trigger a user prompt; remembered ones don't.

Responsible: securityd compares the caller's audit token (cdhash of the binary) against the item's SecAccess ACL. Unknown caller ⇒ delegate to SecurityAgent (L1). Known + "Always Allow" ⇒ release silently.
Crosses in
Caller cdhash, requested operation (decrypt/read), item ACL entries.
Crosses out
A boolean release/deny, plus side-effect: if the user clicks "Always Allow", the caller's cdhash is appended to the item's trusted-app list.
Verify Open Keychain Access.app → "login" keychain → search "Edge Safe Storage" → Access Control tab. You can see which binaries have been granted "always allow" and revoke them.
Trust The ACL match itself runs inside securityd as root. You cannot audit the comparison from userspace; you must accept the mechanism, but you can observe its decisions via Keychain Access.

L5The key blob: what's literally stored in Keychain?

A short opaque string — not an AES key, but the password from which one is derived.

Responsible: the encrypted login.keychain-db file at ~/Library/Keychains/login.keychain-db. The Safe Storage entry is a kSecClassGenericPassword item with service = "Microsoft Edge Safe Storage".
Crosses in
Nothing routinely — written once when Edge first runs and generates the random password, then read-only.
Crosses out
A random-looking ~16-byte base64-encoded string (the "Safe Storage password"), released to authorized callers only.
Trust The on-disk login.keychain-db is itself AES-encrypted under a key derived from your login password — the same password L1 just asked for. Without it, the blob is opaque even with root file read.
Wrong mental model "Keychain is just a glorified plaintext file with permissions." No — it is an encrypted vault whose master key never sits on disk. Even sudo cat login.keychain-db yields ciphertext. The ACL is enforced inside securityd after decryption, not by filesystem permissions.

L6The cookies file: where the secret you actually care about lives

A SQLite database with plaintext cookie names but encrypted cookie values.

Responsible: ~/Library/Application Support/Microsoft Edge/Default/Cookies (file owned by your user, mode 0600). Schema row of interest: host_key='.x.com', name='auth_token', encrypted_value=BLOB. Edge must be closed — it holds an exclusive lock while running.
Crosses in
Nothing from twitter-cli (read-only open). The browser is the only writer.
Crosses out
A BLOB prefixed with the three bytes v10 followed by AES-CBC ciphertext.
Verify lsof | grep "Edge/Default/Cookies" shows whether anything currently has the file open. sqlite3 .../Cookies "SELECT name, host_key FROM cookies WHERE host_key LIKE '%x.com%';" reads names without ever touching values.

L7The decrypt step: why isn't the AES key just stored directly?

Chromium derives the actual AES key from the keychain password using fixed PBKDF2 parameters. Compromise of the cookies file alone yields nothing.

Responsible: twitter-cli's Python code, mirroring Chromium's os_crypt internals.
# Pseudocode (chromium/components/os_crypt internals)
key = pbkdf2_hmac(
  hash_name = "sha1",
  password  = safe_storage_string.encode(),
  salt      = b"saltysalt",
  iterations= 1003,
  dklen     = 16,
)
iv = b" " * 16  # 16 spaces — chromium constant
# encrypted_value blob is "v10" || ciphertext
plaintext = AES_CBC_decrypt(key, iv, encrypted_value[3:])
auth_token = strip_pkcs7_padding(plaintext)
Crosses in
L5 password + L6 ciphertext blob. Both required; either alone is useless.
Crosses out
The literal auth_token and ct0 strings — bit-identical to what your browser sends on every x.com request.
Verify Open Edge devtools on x.com, Application → Cookies, copy auth_token. Compare against what twitter-cli uses (instrument once, then revoke). They match byte-for-byte.
Trust The 1003-iteration count is famously low by modern standards — but irrelevant here, since the input is already a high-entropy random password, not a human-chosen one. Brute force is not the threat model.

L8The replay: how does X tell this is "you"?

It can't, and that's the point. Cookie-auth is bearer-auth; the server has no way to distinguish your browser from your CLI.

Responsible: twitter-cli's HTTP client → https://x.com/i/api/graphql/<query-id>/TweetDetail, with the recovered cookies, the public web bearer, and a x-csrf-token matching ct0.
GET https://x.com/i/api/graphql/<query-id>/TweetDetail?variables=...
Cookie: auth_token=...; ct0=...
Authorization: Bearer AAAAAAAAAA...8FtkA
x-csrf-token: <ct0 value>
x-twitter-active-user: yes
x-twitter-auth-type: OAuth2Session
Crosses in
Your cookies, over your network, indistinguishable from a browser request.
Crosses out
The full TweetResult JSON (text, metrics, media URLs), shaped into the YAML the skill emits.
Wrong mental model "X has rate-limited my CLI separately from my browser." Unlikely. Server-side it is the same session; if you hit a limit it is the session's limit. Distinct CLI fingerprints are at the TLS/headers layer — easy to mimic and not currently a meaningful gate.

Failure mode inventory — which layer broke?

Symptom / errorLayerFix
"Twitter cookie extraction failed in both in-process and subprocess modes" L1 (denied) or L6 (locked) Click Allow; or close Edge to release the SQLite lock.
errSecAuthFailed / dialog re-appears every run L4 (ACL not persisted) Click "Always Allow" once; verify in Keychain Access → item → Access Control.
sqlite3.OperationalError: database is locked L6 Quit Edge fully (not just close window); retry.
Garbled cookie value, decryption "succeeds" but yields binary noise L7 (wrong key derivation) Confirm v10 prefix; iteration count 1003; salt "saltysalt"; 16-space IV.
x.com returns 401 or 403 L8 (or upstream cookie staleness) Re-login in the browser so a fresh auth_token is written; rerun.
x.com returns 429 L8 (session-scoped) Back off; remember rate is shared with your browser activity.
Demystifying recap. The Keychain prompt was not a security theater step — it was the one moment in an eight-layer pipeline where you, the human, sit in the loop. Below the dialog, securityd brokers an ACL check, releases a short random string, and that string feeds a fixed-parameter PBKDF2 that yields the AES key Chromium uses to encrypt one column of one SQLite file. twitter-cli reads that column, decrypts it with the derived key, and replays the recovered cookies against X's normal API. There is no novel cryptography, no Twitter-side cooperation, and no privileged escalation. There is a chain of code-signing-gated boundaries that you can audit at L1, L2, L4, L6, and L7, and that you must trust on mechanism at L3 and L5. That is the entire system.
Env-dependent: macOS 14+ (Sonoma/Sequoia), Edge ≥ 120 / any current Chromium fork. Linux uses libsecret; Windows uses DPAPI; both replace L1–L5 entirely. Iteration count, salt string, and IV constant are taken verbatim from the source trace doc.
