# annotated-flowchart

**Use when:** explaining a process (deploy pipeline, request flow, state machine) as a clickable flowchart with timings and failure paths.

**Data shape:** ordered nodes (rect for action, diamond for decision, circle for terminal), edges with labels, per-node detail (timing, what runs, failure handling).

## Patterns
- `patterns/swimlane-flow.md` — multi-actor lanes × stage columns w/ failure-path edges.

## Gotchas

- (legacy): Inline SVG; arrows need real coords. Don't try CSS for this.
- (legacy): Click-to-reveal node detail (JS toggle a side panel or `<details>` near the diagram).
- (legacy): Show the happy path as solid lines, failure paths as `stroke-dasharray` w/ `--rose`.
- 2026-05-13: when content has linear progression, render TLDR strip as a single line of pills with arrows between (A → B → C).
- 2026-05-13: use <details class="deep"> for genuinely deep optional detail only (log excerpts, edge cases). Never wrap the main narrative in accordions — readers won't open them.
- 2026-05-13: artifacts must be fully self-contained. Inline <style>, inline SVG, inline JS. No CDN links, no @import, no external fonts (system stack is the brand).
- 2026-05-13: never propose edits to exemplar.html — it's the reference. Adapt by rendering a NEW file.

- 2026-07-17: user asked for v2 because the first render was vertical + click-to-reveal detail panel, but they wanted succinctness and explicitly asked to go horizontal (referencing a horizontal swimlane screenshot from an unrelated project as the style target). Fix: for "map every touchpoint in a bundle" asks, default to a horizontal single-row spine with all annotation baked in as static text (small mono fact-lines + one bottom bold callout bar), not an interactive side-panel — interactivity reads as *more* content, which fights succinctness. Also: when the user hands you a categorization scheme (e.g. A/B/C/D) in the same session, render it as a per-node small mono tag line + box border color, not a separate icon/circle badge system — reuses the existing text-density budget instead of adding a new visual grammar.
- 2026-08-01: user asked for v2 because spacing broke — mono sub-lines overflowed node boxes, zebra phase-bands were drawn on arbitrary x-ranges that did not line up with the node columns, and floating edge labels sat on top of the curves they annotated. Fix: define the column geometry ONCE as explicit x/width constants and derive both the node rects and the phase bands from them (bands = column extent ± 8px, never hand-picked ranges); budget ~5.7px per char at mono 9.5px and hard-wrap sub-lines to the box width rather than trusting them to fit; and when a branch needs a label, fold it into the destination node as a small mono "kicker" line instead of floating it on the edge — edges then need no text at all and nothing can collide.
- 2026-08-11: user asked for v2 twice on the same telephony-routing diagram — first because I'd replaced an existing upstream telephony provider with the new one instead of showing it staying in place and forwarding to a single downstream target, second because a plan-tier/billing claim in the diagram ("just 1 account needs to be Pro") needed a live re-check rather than an inferred restatement. Fix: when a revision reframes *which system does what* (not just cosmetic), add a lane per system in actual call/data-flow order (caller → unchanged upstream → new downstream → your infra) instead of collapsing the unchanged system into an annotation on the new one — the user is often testing whether you actually modeled the boundary correctly. And any cost/billing/plan-tier claim baked into a diagram is worth one fresh citation check before a v2 ships, even if it repeats something said correctly earlier in the conversation — carrying an assumption forward silently is exactly what a revision request is often probing for.
- 2026-08-12: same telephony-routing diagram, third v2 — a downstream node in the diagram claimed the API-driven widget could dynamically dial ANY value an external endpoint returned; a second official doc for the same widget explicitly said the opposite ("must define static call paths for each expected response") and I'd surfaced the contradiction to the user instead of silently picking a side. User confirmed the constrained reading. Fix: when two primary-source docs for the same mechanism disagree, do not average or blend them into the diagram — pick neither until confirmed, say so in-artifact, and once confirmed, correct the SPECIFIC misleading node (retitle it, fix its downstream edge label, add a small caption table naming the concrete pre-wired mapping) rather than re-explaining the whole flow in prose. A caption table under the SVG (label → widget → target) is cheaper than redrawing three new boxes into an already-tight lane.
- 2026-08-14: user asked, mid-render, whether to leverage PlantUML instead of hand-coded inline SVG with manually computed edge coordinates — the exact class of bug this recipe's 2026-08-01 entry already warns about. Checked first whether `plantuml`/`dot`/`java` were actually installed locally (they were); this changes the calculus, since local rendering keeps the shipped artifact self-contained (render once to static SVG, embed only the output, strip the `<?plantuml-src...?>` re-edit PI, no runtime dependency survives). Fix: for a genuine pipeline/component/process diagram, render via `plantuml -tsvg` with skinparams mapped to the Anthropic palette (stereotypes like `<<custom>>`/`<<buy>>`/`<<ghost>>` double as both semantic tags and color/border selectors) and embed the static SVG output as `<svg class="flow" viewBox="...">...</svg>` inside the normal `.canvas` wrapper — auto-layout (Graphviz `dot`) eliminates hand-picked bezier coordinates entirely, which is strictly better once the toolchain is confirmed present. Do NOT do this for an ERD that is deliberately non-relational (a hub-and-spoke "sources through one mapping mechanism into one canonical fact table" shape, not FK-joined tables): PlantUML's `entity`/`||--o{` notation assumes conventional table cardinality, and forcing an intentionally-unconventional structure through it fights the exact point the diagram exists to make — keep those hand-drawn with an explicit non-schema disclaimer above them. Toolchain not installed → fall back to hand-coded SVG per the existing entries below, do not add a PlantUML dependency the render can't complete without.
- 2026-08-23: rendered a business-model/money-flow map as a hub-and-spoke (every actor node wired to a central "platform" hub); user asked for v2 because that layout overstates how centralized the business actually is — most money moves actor→actor (customer pays merchant, employer pays staff) and the platform only taps a fee on the way through. Fix: for "who touches the product / how do they make money" asks, default to a source → rail(with fee taps) → destination flow-through layout (Sankey-like: money enters left, exits right, the platform is a thin conduit in the middle with tap points branching to a revenue/cost annex), not a hub-spoke star — reserve hub-spoke for cases where the center genuinely IS every counterparty (e.g. a literal message broker). Also worth keeping from this pass: a deliberately-disconnected node (dashed rust, no line touching the rail) to show a real flow that does NOT go through the platform (a peer-to-peer cash transfer bypassing the wallet entirely) — that absence was as informative as the connections.
